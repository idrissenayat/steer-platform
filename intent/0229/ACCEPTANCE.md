# Acceptance boundary

Development acceptance requires the actual HTTP handler and encrypted SQL stores
to assemble and recover one exact original without another operation, model
reservation or workflow start. Incomplete source coverage cannot admit work.
Source/choice/configuration changes, holds, missing grants and revoked permission
must not become prepared acknowledgements. Originals and newer drafts remain intact.

Recorded SDK/Temporal integration fixtures now call the preparation endpoint before
starting work. Their identities, evidence inventory/lifecycle assertions, preparation
authority and model responses remain synthetic. They are not real permitted-corpus
proof, semantic accuracy, human UI acceptance, independent Test Agent approval or
a saved repository bundle. A prepared receipt never completes I1–I6.

The current production evidence/authority service, actual editor connection and
real records activation are not included. D1 remains unsigned/inactive and the real
migration baseline remains held. No paid call, runtime Git saving, gate, deployment,
release or deletion is authorized. Signed sources remain unchanged.
